# Универсальный GATT client и реальный Heart Rate

Реализовано 23.10.2026 по поручению владельца. Это экспериментальный активный
BLE слой. Пассивный просмотр рекламы и ручное добавление экземпляра по-прежнему
не подключаются к удалённому устройству: соединение начинается явной командой.

## Границы и интерфейсы

`include/NaBTools/bt/gatt/client.hpp` не зависит от ESP-IDF, CBOR или профиля HRM.
Опциональный `IBackend::gatt()` возвращает `IGattClient*`; отсутствие транспорта
допустимо. `BtEngine::gatt()` передаёт этот механизм модулям. `IDevice::on_attached`
получает runtime ID; `on_gatt` принимает события только в контексте движка.

| Операция IGattClient | Содержание |
|---|---|
| connect(owner, address, request, session) | Резервирование сеанса и асинхронное подключение |
| disconnect(session, request) | Закрытие сеанса |
| discover(session, optional UUID, request) | Сервисы, характеристики, дескрипторы, завершение |
| subscribe(session, value handle, CCCD handle, indications, request) | Notify или Indicate |
| read(session, handle, request) | Чтение характеристики |
| write(session, handle, bytes, with response, request) | Запись характеристики |
| cancel(owner) | Отмена операций/соединений удаляемого экземпляра |
| take(event), stats() | События и ограниченные счётчики транспорта |

UUID16/32 нормализуются в UUID128 (`core/uuid.hpp`); сохраняются UUID128,
handles, связи descriptor→characteristic→service и свойства характеристики.
`GattEvent` владеет до 512 байт данных. В нём отдельно передаются DeviceId,
GattSessionId, request_id, время, переносимый status и числовая ошибка backend.
`ok` команды означает принятие; окончательный результат приходит событием.

DeviceId и GattSessionId имеют независимые поколения. При удалении движок
отменяет ресурсы владельца, а затем разрушает объект. Удаление из Action
откладывает разрушение до возврата из callback. Поздние события старого поколения
не доставляются новому объекту. Вызовы транспорта выполняются последовательно
на задаче движка; из SDK callback вызывать методы прибора нельзя.

## ESP-IDF backend

`backends/espidf/gatt_client.*` включается `CONFIG_NABTOOLS_GATT_CLIENT=y`
(по умолчанию выключен), вместе с `CONFIG_BT_GATTC_ENABLE=y`.
SDK callback копирует данные в owned очередь; `pump` переносит их в события
движка. Discovery выполняется порциями, а не одним большим временным деревом.

Текущие пределы: 4 логических слота (контроллер C6 настроен максимум на 3 BLE соединения),
32 входных SDK события, 32 выходных события,
16 диапазонов сервисов и 8 зарегистрированных подписок на сеанс; read/notify/
write до 512 байт. Одна ATT операция на сеанс и одно инициирование соединения
одновременно. Регистрация notify сериализована между сеансами, поскольку SDK
не передаёт conn_id в её завершении. Эпоха SDK соединения защищает от повторного
использования conn_id. Переполнение вызывает ошибку и закрытие затронутых
активных сеансов; dropped доступен в research snapshot.

Подключение/ожидание ограничено 30 секундами, ATT/discovery — 15 секундами.
В этой версии IDF нет публичной отмены уже начатого open: логическая отмена
выполняется сразу, слот остаётся в карантине до SDK OPEN, поздний успех закрывается.
Pairing UI, хранение bonds, автоматическое повышение security, GATT server,
long/prepared writes и восстановление экземпляров после reboot не реализованы.
Read/write используют characteristic API; универсальный редактор дескрипторов
и полный интерактивный GATT explorer остаются следующими задачами.

На реальном C6 выявлены и учтены особенности SDK:

- Инициирование при работающем extended scan возвращало error 133. Backend
  приостанавливает scan до OPEN, затем восстанавливает запрошенное приложением
  состояние. После подключения сканирование и уведомления работают совместно.
- В IDF 5.4 `get_all_char/get_all_descr` возвращают общий count кеша, даже когда
  буфер рассчитан на одну запись. Перебор ограничивается отдельно полученным
  attr_count; успешная непустая страница содержит одну запрошенную запись.

SDK и соседние проекты не исправлялись. Основания: локальные исходники
`btc_gattc.c` и [официальный GATTC API ESP-IDF 5.4](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32c6/api-reference/bluetooth/esp_gattc.html).

### Почему пауза сканирования, проверка источников

После замечания владельца проверены документация, SDK 5.4 и первичные источники.
Сотрудник Espressif прямо рекомендует stop scan → connect → restart scan в
[issue 4562](https://github.com/espressif/esp-idf/issues/4562), где описан тот же
status 133. Обсуждение относится к старому ESP32/IDF 4.0 и не доказывает
конкретный дефект C6/5.4. Но тот же порядок есть в
[официальном BLE 5.0 client примере v5.4](https://github.com/espressif/esp-idf/blob/v5.4/examples/bluetooth/bluedroid/ble_50/ble50_security_client/main/ble50_sec_gattc_demo.c)
и [описании GATT Client Espressif](https://docs.espressif.com/projects/esp-techpedia/en/latest/esp-friends/get-started/case-study/BLE-examples/gatt-client-example.html).

Bluetooth различает Scanning, Initiating и установленный Connection.
[Core, LL §1.1.1](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/low-energy-controller/link-layer-specification.html)
разрешает несколько машин состояний, но не требует от реализации поддержки
всех их сочетаний. Поэтому успешное scan + established connection не доказывает
поддержку scan + initiating, а общей фразы «Bluetooth запрещает это» быть не должно.

В нашем SDK `ESP_GATT_ERROR=0x85` — generic error, не расшифровка причины HCI.
Исходное наблюдение: scan/open → 133, stop/open → реальное соединение; это
обосновывает рекомендуемую последовательность в данном backend. Точная причина
того отказа (конфликт controller states, очередь host или scheduling/coexistence)
не установлена: соответствующего HCI command/status в исходной записи нет.
Для доказательства потребуется ограниченная запись HCI непосредственно при
повторном отказе, а не вывод причины из одного кода 133. SDK не обновлялся;
найденные обсуждения других версий не объявлены причиной нашего случая.

Backend ждёт успешного GAP EXT_SCAN_STOP_COMPLETE, затем начинает open;
после OPEN возобновляет только ранее запрошенный scan. Фиксированной задержки,
ветки Garmin и выключения сканирования на всё время GATT-сеанса нет.

## Отдельный профиль Heart Rate

`profiles/heart_rate` знает стандартные UUID 180D / 2A37 / 2902 и опциональный
2A39; движок и аппаратный backend этих UUID и Garmin не знают. Команда Connect
запускает connect → discovery → subscribe. Уведомления разбираются существующим
декодером и выдаются независимыми STRUCT/CBOR Actions. Reset energy доступен
только при найденном writable control point. На нашем Garmin он не обнаружен;
команда не отправлялась. Протокол — [Bluetooth HRS 1.0](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/HRS_v1.0/out/en/index-en.html).

Состояния идут схемой `nabtools.bluetooth.hrm.state.v1`, измерения —
`nabtools.bluetooth.hrm.measurement.v1`. Повтор одинакового BPM тоже является новым
измерением. Отсутствующие contact/energy/RR не подменяются выдуманными значениями.
Подробности outputs и синтетических тестов — [профиль HRM](readme_hrm_ru.md).

## Исследовательское приложение и вебка

Слева — таблица выбора экземпляров. Справа — название, MAC/ID, команды, события
и полученные сообщения CBOR выбранного экземпляра. «Все сообщения» — отдельный
режим без команд конкретного прибора. Viewer обходит произвольные CBOR поля;
специальных веток Garmin/HRM/SmartTag в нём нет.

Команды защищены boot_id и поколением экземпляра; результаты приёма команды
и её выполнения различаются. Полный снимок и изменения передаются одним
[форматом WS/CBOR](readme_websocket_ru.md). HTTP обслуживает файлы сайта.

## Проверки и пределы

На ESP32-C6 подтверждены стандартный Heart Rate, реальные GATT notifications,
вывод измерений через CBOR, Disconnect, повторное подключение и удаление
подключённого экземпляра. При удалении освобождается транспорт; история сообщений
не превращается в действующий экземпляр.

В исследовательском приложении периодические heap-копии полного состояния
заменены двумя ограниченными буферами. Передача удерживает опубликованный буфер,
а задача BT пишет только в свободный. Медленный клиент не блокирует BLE и не
создаёт неограниченную очередь снимков. Длительную стабильность и насыщение всех
лимитов следует проверять отдельно для конкретной конфигурации.

Native тесты проверяют routing, generation и удаление из callback с fake GATT.
Профиль проверяется в режимах STRUCT/CBOR/BOTH. Реальная приёмка произвольных
read/write, security и нескольких устройств не выполнялась. SmartTag button/ring
требуют отдельного аутентифицированного драйвера.

Текущий прикладной транспорт: [единый поток WS/CBOR](readme_websocket_ru.md).
