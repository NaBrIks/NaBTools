# Уточнение: SIG вне обязательного образа и ответственность приложения

Исторический этап обсуждения 23.10.2026. Замечания о наличии старой реализации
ниже относятся к той дате; текущее состояние — [аудит](readme_retired_code_ru.md).

**Промежуточный вариант.** Следующее [уточнение владельца](readme_sig_outputs_bt_ownership_ru.md)
допускает SIG на MCU как отключаемый модуль с профилями, прямые protocol outputs
и владение runtime-устройствами BT-подсистемой. Предложение DeviceOwner у приложения
ниже больше не является основным вариантом. Размеры исходников остаются фактами.

Дата: 2026-10-23. Статус: уточнение требований владельца и обновлённое
предложение, **без реализации**. Этот документ заменяет прежние рекомендации
об обязательном SigCatalog в BtEngine и автоматическом lifecycle устройств
из readme_interfaces_proposal_ru.md. Конкретные интерфейсы остаются предложением.

## Что уточнил владелец

- Полный SIG слишком велик для обязательного включения в прошивку.
- Нужно рассмотреть не только создание, но и удаление экземпляров и обязанности сторон.
- Библиотека предоставляет механизмы; работа и решения конкретного приложения
  относятся к приложению. Формулировка «скорее всего» не закрепляет окончательно
  конкретную C++-модель владения.
- Исследовательская ценность SIG и работа по именам сохраняются.

## Размещение SIG

Полный upstream — источник для разработки и инструмента исследований на ПК.
Он не обязан попадать в firmware, библиотеку engine или каждый event payload.

| Режим | Что находится на MCU | Где полные имена и описания |
|---|---|---|
| Рабочая прошивка | Типизированные коды и декодеры выбранных профилей; небольшой набор нужных имён по опции | Внешний инструмент/сервер, если он подключён |
| Исследование с ПК/веб-сервером | Raw + разобранные данные, состояния, capabilities и версия протокола событий | Полный каталог у принимающего инструмента |
| Самостоятельное исследование на MCU | Выбранный именованный subset | Только этот subset; расширение через настроенное внешнее хранилище возможно отдельно |

Разрешение по именам сохраняется в research API, но выполняется там, где загружен
соответствующий каталог. Host может разрешить имя в UUID/typed selector и отправить
конкретную команду MCU. Для прошивки известного HRM-профиля достаточно генерируемой
типизированной константы UUID, без всей базы или длинного description.
Необязательно отправлять длинный identifier/name вместе с каждым пакетом;
типизированный код и компактные данные позволяют обогатить событие при приёме.
Символические имена прикладных событий — самостоятельный контракт, их это не отменяет.

Не найдено в embedded subset, неизвестно полному SIG, нет внешнего каталога и
неподдержанный decoder — разные состояния. Локальная прошивка не обещает полные
имена без нужных данных; подключённый full research показывает все доступные
имена и исходные коды. Произвольное требование «всё в имени» не должно незаметно
тащить весь upstream в образ.

Предлагаемая коррекция API:

```cpp
BtEngine(std::unique_ptr<IBtBackend>, EngineConfig); // без обязательного SigCatalog
ResearchModule(INameResolver&, ResearchOptions);   // resolver выбран приложением
```

INameResolver — необязательная зависимость конкретного research/rendering-модуля,
не ядра BT. Возможные реализации: embedded subset, host full catalog, явно
настроенный external-storage provider. Устройства/приложение выбирают бюджет,
а генератор вырезает subset по manifest профилей, а не линкует всё «на всякий случай».
На ПК upstream по-прежнему обновляется и проверяется согласованно с derivatives;
это не означает обновления всех прошивок или загрузки туда новых YAML.

## Обязанности по устройствам

| Сторона | За что отвечает |
|---|---|
| Приложение | Какие приборы нужны; когда создавать, связывать, заменять и удалять; постоянная конфигурация, identity policy, TTL и привязки к бизнес-объектам |
| Recognizer | Выдаёт кандидатов/признаки. Не создаёт и не удаляет постоянные приборы |
| Factory, если нужна | Строит запрошенный driver. Не выбирает момент создания и не определяет lifetime |
| Engine | Доставка в зарегистрированный экземпляр, операции/сеансы, безопасное техническое отсоединение и завершение pending callbacks |
| Driver/handler | Протокол/декодирование и собственное состояние; освобождение своих ресурсов при остановке |
| Наблюдатели/веб/LVGL | Подписки и owned snapshots; не являются неявными владельцами Device |

Обязательная admission policy внутри engine не нужна. Приложение может реагировать
на Candidate callback самостоятельно. Опциональный DiscoveryTracker в примере
может автоматизировать создание/TTL для сканера, но это отдельная явно подключённая
политика, не поведение core по умолчанию. Ограниченный кэш наблюдений имеет свой
технический eviction; его очистка не удаляет настроенные экземпляры приложения.

## Кто физически владеет C++-объектом

Решать «нужен ли прибор» и удерживать память до завершения callback — разные задачи.
Есть две пригодные схемы:

| Вариант | Плюсы | Обязательство |
|---|---|---|
| Приложение держит объект, engine заимствует ссылку | Прямое и явное владение объектом приложения | До delete нужен detach и barrier; случайный delete во время callback опасен |
| Приложение держит DeviceOwner, engine хранит переданный unique_ptr | Приложение управляет сроком жизни, engine обеспечивает безопасное техническое разрушение | Нужен контракт асинхронного close и generation handles |

Рекомендую второй вариант для первого asynchronous API. Он не передаёт engine
решения о нужности прибора. Приложение создаёт driver и передаёт его библиотеке,
сохраняя move-only ownership token. Реестр внутри engine — техническая таблица
маршрутизации и владения, а не менеджер автопарка.

Эскиз скорректированного API:

```cpp
Result<DeviceOwner> BtEngine::attach_device(
    DeviceSpec, std::unique_ptr<IDeviceDriver>);

class DeviceOwner {
public:
    DeviceHandle handle() const;   // невладеющий ID + generation
    Request<void> close();         // начать удаление, получить завершение
    // destructor инициирует close, не блокирует callback/task
};
```

Attach возвращает token после проверки и резервирования слота; техническая
активация может ещё находиться в attaching. Состояние/результат старта публикуется
явно. Неудачный attach не оставляет зарегистрированных ролей/ресурсов.
Синтаксис и окончательная модель token ещё подлежат согласованию.

## Удаление и завершение

1. Приложение вызывает close либо уничтожает DeviceOwner по собственному решению.
2. Device помечается closing. Новые адресуемые ему операции отклоняются;
   повторный close идемпотентен.
3. Engine прекращает доставку новых live callbacks этому handler, отменяет его
   pending operations и освобождает принадлежащие ему leases/подписки.
4. Завершается текущий callback; SDK completions проверяются по generation.
   Общее соединение не разрывается, пока оно нужно другим владельцам leases.
5. Driver выполняет stop; engine удаляет объект и освобождает slot.
6. Close Request завершён. Старый DeviceHandle возвращает expired, даже если
   numeric slot уже занят новым объектом.

Close не ждёт внутри engine callback. Внешнее приложение может дождаться Request
в своём контексте. Destructor token только запускает безопасный процесс; слот/объект
нельзя физически освободить до barrier. Такой cleanup не должен теряться из-за
полной общей очереди. При engine shutdown применяется то же завершение, tickets
и owners после уничтожения движка безопасно становятся expired.

Уже доставленные owned EventSnapshots могут храниться у логгера после удаления
Device: они содержат данные/ID/generation, а не указатель на handler. Close
не обещает стереть записанную историю или удалить все копии snapshots у потребителей.
Business stale/offline не равняется close: приложение само выбирает реакцию.

## Что больше не считать рекомендацией по умолчанию

- Обязательный SigCatalog в constructor BtEngine/ModuleContext.
- Полный SIG/длинные descriptions в каждой firmware и каждом callback.
- Автоматическое создание Device на каждый найденный MAC/распознанный тип.
- Встроенный TTL, автоматически удаляющий прикладные Device.
- Удержание Device любым невладеющим observer или случайной подпиской на логи.

Более ранний proposal полезен как набор обсуждавшихся механизмов; при расхождении
по этим вопросам действует данное уточнение. Реализация по-прежнему legacy.
