# Уточнение: подключаемый SIG, прямые выходы данных и владение BT

Это сохранённый этап проектирования. Описания legacy-кода относятся к исходному
снимку; текущие модули реализованы отдельно, а старый код удалён после переноса.
См. [аудит 29.10.2026](readme_retired_code_ru.md) и [runtime](readme_runtime_ru.md).

Дата: 2026-10-23. Статус: текущие уточнения владельца и предложения API,
**без реализации**. Этот документ заменяет предыдущие рекомендации:
обязательный внешний full SIG, обязательный typed payload/универсальный
сериализатор перед CBOR и прикладной DeviceOwner как основной lifecycle.
Утверждённый ADR о центральном движке/модулях остаётся в силе.

## Что следует из последнего обсуждения

- SIG допустим в прошивке отдельным подключаемым модулем, управляемым config.
  Прикладная прошивка может полностью обойтись без него.
- Владелец предлагает 2–3 объёма SIG: распространённое, расширенное и всё.
  Конкретные списки и критерий распространённости пока открыты.
- Для TPMS возможны непосредственный struct-output, CBOR-output или оба.
  Универсальная промежуточная модель не должна быть обязательной ценой CBOR.
- После получения/декодирования нужен прикладной Action; его реализация
  принадлежит приложению, а не конкретной очереди/веб-серверу библиотеки.
- Текущее рабочее направление владельца: экземпляры принадлежат BT-подсистеме.
  Уведомления могут быть системными или адресованными конкретному прибору.
  Уничтожение всей BT-подсистемы не является обычным сценарием использования.

Имена config, интерфейсы Action, состав SIG-пакетов и точный API registry ниже
ещё являются предложениями, не реализованными контрактами.

## 1. SIG — необязательный модуль с профилем данных

Предлагаемый набор профилей:

| Профиль | Содержимое |
|---|---|
| OFF | Нет каталога SIG/поиска/длинных descriptions; нужные драйверу typed UUID/constants остаются независимыми |
| COMMON | Основные служебные коды, выбранные сервисы/характеристики, список распространённых компаний и записей используемых профилей |
| EXTENDED | COMMON плюс расширенный курируемый список |
| FULL | Все поддержанные генератором выбранные разделы SIG; ограничения coverage всё равно явные |

Пример будущей конфигурации, сейчас **не существующие флаги**:

```text
NABTOOLS_SIG_PROFILE = OFF | COMMON | EXTENDED | FULL
NABTOOLS_SIG_DETAILS = NAMES | DESCRIPTIONS
NABTOOLS_TPMS_OUTPUT = STRUCT | CBOR | BOTH
```

Профиль отвечает за отбор записей, details — за глубину: полный список компаний
по именам и полные тексты GSS имеют разную стоимость. FULL не означает,
что автоматически реализованы codecs всех значений или что образ влезает на
любую плату. Для каждой поддерживаемой конфигурации впоследствии нужна проверка
map/flash/RAM. Размер upstream YAML не выдаётся за размер бинарного каталога.

Full research может использовать встроенный каталог подходящей прошивки,
настроенное внешнее хранилище или host catalog. Режим работы по именам сохраняется
для загруженных определений; отсутствующее в subset не объявляется неизвестным
всему Bluetooth. Прикладной TomTom/HRM decoder не зависит от NameResolver.

### Кто составляет COMMON/EXTENDED

SIG назначает коды и имена, но не предоставляет в используемых таблицах рейтинг
частоты устройств в эфире. Первые/последние/малые company ID не являются таким
рейтингом. Пример «100 наиболее вероятных» — желаемый объём, не измеренный top-100.

Рекомендуется хранить reviewable manifests отбора отдельно от upstream:
company IDs и canonical definition identifiers с причинами включения. Начальный
список составляет сопровождающий проекта; приложение может добавить свой набор.
Генератор строит closure зависимостей выбранных definitions: UUID, units,
flags/enum labels и другие необходимые связи. Включённый профиль может объявить
минимально нужные ему definitions без принудительного включения всего SIG.
Список автоматически дополняется только объявленными зависимостями, а не всеми
записями, добавленными upstream.

Позже локальные captures сканера могут дать частоты наблюдений и кандидатов для
пересмотра списка. Это статистика конкретного окружения, а не универсальная
популярность брендов. Несколько advertisement от одного прибора и random MAC
не должны выдавать ложную статистику количества уникальных приборов.

Обновление upstream/derivatives из прежнего предложения сохраняется. При нём
проверяются имена/ссылки manifests, переименования, неизвестные entries и размеры
каждого пакета. Подключать весь новый upstream в COMMON автоматически нельзя.
Ни submodule, ни updater, ни эти profiles сейчас не реализовывались.

## 2. Кто формирует CBOR в TPMS

CBOR-представление TPMS формирует **TPMS-модуль**, поскольку он знает поля,
единицы, смысл alarm и предметную схему. Core BtEngine не переводит произвольные
прикладные объекты в обязательный общий формат. Выбранная библиотека CBOR —
техническая зависимость опционального output, а не всех пользователей nabtools.

| Режим | Результат | Чего не требуется |
|---|---|---|
| STRUCT | Типизированное TpmsReading и вызов typed Action | CBOR dependency, создание JSON, универсальная reflection schema |
| CBOR | Прямое кодирование TPMS-пакета и вызов CborAction | Обязательный публичный TpmsReading или JSON DOM перед кодированием |
| BOTH | Оба выхода | Две независимо сопровождаемые версии протокольных правил |

Если CBOR не нужен, потребителю обычно нужно само измерение: typed callback,
доступ к latest state, свой alarm evaluator или преобразование в другой формат.
Не требуется заставлять его разбирать CBOR обратно, чтобы получить давление.

Режим выбирается при сборке модуля. Unused encoder и его зависимости не должны
попадать в STRUCT-only сборку; отсутствие этого доказывается последующей
сборкой/map, а не одним наличием config-флага. Это режимы одной реализации,
а не три расходящиеся копии TomTom decoder.

Сохраняется одна проверенная трактовка wire fields, signedness и единиц.
Общие маленькие helpers чтения байтов/перевода единиц допустимы; обязательная
виртуальная цепочка на каждое поле, универсальный AST, variant или JSON ради
двух выходов не предлагаются. Выбор struct/direct-CBOR branch и совместное
чтение полей для BOTH уточняются по реальному коду и измерениям.
Эквивалентность двух выходов проверяется эталонными пакетами.

### Версии схем и оптимизация

Schema version CBOR не равна версии библиотеки и не равна флагу STRUCT/CBOR.
Если нужны разные CBOR-контракты, выбирается конкретный encoder/schema; нельзя
менять смысл ключа или единицы незаметно под тем же schema ID.
Общая будущая схема BT/433 может быть независимым контрактом TPMS, который
применяют оба output-модуля. Окончательные имена ключей/единицы ещё не утверждены.

Текущий legacy-код не является уже готовым CBOR-only output: TomTom SendEvent
сейчас создаёт TPMSData, JSON DOM, JSON string и CBOR, затем отправляет struct
через esp_event. Разделение режимов — будущая работа. Нельзя заявлять размер/
скорость/нулевые аллокации direct-CBOR до выбора encoder и проверок.

## 3. Action — точка прикладного подключения

Путь CBOR: backend → engine → TomTom handler → TPMS CBOR encoder → Action → приложение.
Путь STRUCT: backend → engine → TomTom handler → typed Action → приложение.

Минимальный эскиз, не заголовок API:

```cpp
struct CborAction {
    void* context;
    DeliveryResult (*invoke)(void*, const MessageInfo&, CborView);
};

struct TpmsAction {
    void* context;
    DeliveryResult (*invoke)(void*, DeviceId, const TpmsReading&);
};
```

Обычная пара function pointer + context достаточна для минимального варианта;
удобная std::function/лямбда-обёртка возможна сверху. Action здесь не язык команд
и не обязательная связь с lvgl-cbor actions. MessageInfo сообщает тип/schema,
устройство и время; его окончательная форма обсуждается.

Модуль вызывает Action после успешного разбора и формирования выбранного
результата, в контексте обработки engine, не в SDK callback. Malformed input
сообщается отдельной диагностикой, не выдаётся за успешное TPMS-измерение.
Callback должен быть коротким. Долгий web/диск/сеть выполняются прикладной задачей.

CborView/TpmsReading в этой форме заимствованы до возврата Action. Если код
приложения отправляет сообщение в асинхронную очередь, он копирует необходимые
байты/данные. Позже возможен отдельный owned-buffer Action с передачей владения;
его нельзя неявно подменять сохранением span на stack buffer.
DeliveryResult отражает accepted/dropped/error. При переполнении прикладной
очереди BT учитывает ошибку/потерю, но не ждёт секунды и не выбирает сам
конкретную очередь/esp_event_base/HTTP endpoint. Retry policy задаётся явно.

Одного Action на выход достаточно для первого API. Fan-out, esp_event bridge,
CBOR queue, webhook или запись реализует ваш callback/необязательный adapter.
Ни один из этих вариантов не требует глобальных weak CBOR_loop/CBOR_EVENT.

## 4. Принадлежность BT-подсистеме

Рекомендуемая рабочая схема после уточнения владельца:

| Объект | Владелец и ответственность |
|---|---|
| BtSubsystem | Долгоживущий сервис приложения, создаваемый при запуске прошивки |
| BtEngine, backend, runtime registry | Принадлежат BtSubsystem |
| Device/driver handlers | Создаются, хранятся и безопасно удаляются BT-подсистемой |
| Конфигурация нужных приборов | Прикладное постоянное хранилище; передаётся BT-подсистеме |
| Данные о колёсах/сезоне/технике | Приложение; ссылается на DeviceId, не владеет объектом BT |
| Action | Прикладной код и его context; регистрация удерживается по согласованному lifetime |

BtSubsystem можно оформить как фасад композиции engine + modules + registry,
а не второй движок/задачу. Название класса и точная граница facade ещё обсуждаются.
Приложение передаёт конфигурацию и команды add/remove; BT решает техническое
создание/сопоставление и осуществляет безопасный lifecycle. Правила
автоматического добавления незнакомых кандидатов остаются явной политикой,
а не обязательным созданием экземпляра на каждый MAC.

Прикладной DeviceOwner/RAII token, исчезновение которого удаляет прибор,
больше не является рекомендуемым основным API. Внешнему потребителю достаточно
невладеющего проверяемого DeviceHandle/DeviceId. Закрытие страницы/логгера
снимает их подписку и не удаляет физический прибор из BT.

Для конкретного устройства BT хранит его собственные Actions/настройки
обработки. Для общих событий — отдельные system hooks: готовность стека,
ошибка backend, scan state, connection state и диагностические сообщения.
Для per-device output и system notifications не требуется один обязательный
универсальный сериализатор. Общая metadata/идентичность может использоваться вместе.

Примерные операции facade: add_known_device(spec), remove_device(id),
set_device_actions(id, actions), device_snapshot(id). Подробные сигнатуры
нужно согласовать отдельно от прежних attach/DeviceOwner предложений.

## 5. Удаление конкретного устройства всё равно нужно

Долгоживущая BT-подсистема не означает вечную жизнь каждого driver.
Смена датчика/конфигурации, удаление временного исследовательского объекта
или явный remove требуют следующего механизма:

1. Отметить экземпляр removing и прекратить новые адресованные ему операции.
2. Убрать маршрутизацию и не начинать новые его Actions/callbacks.
3. Завершить текущий callback, отменить pending и освободить собственные leases.
4. Не разрывать общий ресурс, пока он нужен другим пользователям.
5. Освободить handler; старые handles/completions проверять по generation.

Операция удаления может возвращать completion ticket, если вызывающему коду
нужно знать момент завершения. Выходы already-owned сообщений могут храниться
в очереди/истории после удаления — они не содержат указатель на handler.
Context прикладного Action нельзя уничтожать до завершения его текущего вызова;
замена Actions также требует безопасной границы. Отписка и удаление устройства
различаются.

Нормальный сценарий — один запуск BT на время работы прошивки. API полного
shutdown/hot-unload и сложный restart lifecycle не являются приоритетом.
Минимальный корректный cleanup для ошибок/тестов возможен, но не должен
определять основную пользовательскую модель.

## Что сохраняется открытым

- Конкретные COMMON/EXTENDED manifests, целевой размер и число компаний.
- Encoder CBOR, схема TPMS и значения build config по умолчанию.
- Точный Action signature, owned-buffer path, число Actions на устройство.
- Граница facade BtSubsystem и engine; детали add/remove factory API.

Этот документ фиксирует текущий вариант для обсуждения, не разрешение реализовать
все механизмы. Исходники, генераторы и SIG при этом обсуждении не менялись.
