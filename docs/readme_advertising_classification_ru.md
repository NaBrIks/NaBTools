# Классификация по рекламе и режимы сканирования

Реализовано 29.10.2026. Классификатор исследует уже полученные advertising/scan
response пакеты. Он не подключается, не спаривается и не создаёт экземпляры
устройств. Добавление и GATT-команды остаются отдельными явными действиями.

## Тип и возможности

Переносимый API: `<NaBTools/bt/gap/classification.hpp>`,
`classify_advertisement(AdvertisementView)`. Он не требует SDK, CBOR или SIG
каталога. Возвращает ограниченные типизированные факты:

- `type`: предполагаемый вид устройства, источник, уровень доказательства и
  исходное численное значение Appearance/UUID;
- `capabilities`: до шести признаков с источником и численным UUID;
- `conflict`: несовместимые варианты одинакового приоритета;
- `truncated`: часть признаков не поместилась. Исходный пакет не обрезается этим
  классификатором и остаётся доступен в исследовательских raw-данных.

Приоритет: распознанный и разобранный протокол модуля, затем Appearance,
объявленный сервис, затем подсказка по имени. Неподтверждённая сигнатура модуля
не вытесняет явный Appearance. Классификатор не использует компанию или MAC-OUI
для вывода «телефон/часы/пульт». Драйверы могут дополнить `Detection::kind`;
движок лишь передаёт результат, не содержит правил Samsung/TomTom.

Первые типы: телефон, компьютер, часы, пульт, клавиатура, мышь, джойстик,
геймпад, метка, пульсометр, термометр, тонометр, велодатчик, весы, датчик среды
и датчик шин. Это выборочное покрытие Appearance/сервисов, а не все устройства SIG.
Неподдержанные поля и UUID сохраняются в обычном AD/raw представлении.

Из стандартных сервисов распознаются Heart Rate, HID, Battery, Device Information,
Health Thermometer, Blood Pressure, Cycling Speed/Cadence, Cycling Power,
Running Speed/Cadence, Weight Scale, Environmental Sensing, Immediate Alert,
Link Loss. Поддержаны объявления UUID 16/32/128 bit и Service Data; vendor UUID
не интерпретируется как стандартный по совпадению части байтов.
Service Solicitation означает **запрос** сервиса и не выдаётся за его наличие.

Имя `SmartRemote` даёт только «пульт ?». HID означает функцию устройства ввода,
но сам по себе не позволяет выбрать между пультом, клавиатурой и мышью.
Appearance часов вместе с Heart Rate означает «часы, объявлен пульс».
Объявление сервиса не доказывает доступность GATT, разрешение на чтение,
наличие измерения в рекламе или успешную работу функции.

Повреждённые AD и extended fragments не дают новых заключений. Исследователь
держит рекламу и scan response раздельно для одной пары address/type/SID;
каждая новая половина заменяет собственные признаки. Другая половина учитывается
не дольше 30 секунд относительно последнего пакета. Ротация адреса не объединяет
устройства по похожему имени. Возможности ограничены, их неполнота видна явно.

## CBOR и вебка

В observation добавлена `classification`:

```text
type: "remote_control"
strength: "hint"                 # unknown / hint / advertised / decoded
source: "local_name"             # appearance / service_uuid / service_data / handler
value: 0                        # исходный Appearance/UUID, если есть
conflict: false
truncated: false
capabilities: [{key: "hid", source: "service_uuid", value: 6162}]
requested: []                   # запрашиваемые, не предоставляемые сервисы
```

В таблице видны отдельные колонки «Тип», «Возможности», «Основание».
Все сортируются и участвуют в фильтре. Подробности доступны через tooltip и
исходный CBOR. UI переводит готовые ключи и не определяет устройства по имени.
Компания остаётся первой колонкой, строки однострочные; узкий экран использует
горизонтальную прокрутку. Обновления сохраняют DOM-узлы и выделенный текст.

## Активное и пассивное сканирование

`ScanMode::{passive,active}` и `BtEngine::set_scan_mode` задают режим через
`IBackend`. Старый пользовательский backend без этого метода возвращает
`unsupported`. В ESP-IDF режим можно задать до старта и менять во время работы.
По умолчанию он пассивный. Постоянное хранение выбора не добавлялось.

ESP-IDF-специфичный `EspIdfScanTiming` задаёт interval/window в единицах 0.625 мс.
Диапазон API библиотеки: 4..0x4000, 4 <= window <= interval. Default 0x80/0x30
сохранён; одинаковые значения запрашивают непрерывное окно, но не гарантируют
непрерывный доступ к радио при coexistence. Конструктор `EspIdfBackend(timing)`
и `set_scan_timing(timing)` принимают настройку; неверная возвращает invalid
до SDK. `scan_timing()` — фактически подтверждённая настройка, `{0,0}` до
первого успешного completion; `requested_scan_timing()` и
`scan_timing_pending()` показывают запрос и ожидание. Pending в общей
scan-конфигурации учитывает также смену таймингов. Все вызовы — owner-context.

Пассивный режим принимает рекламу. Активный дополнительно запрашивает Scan
Response у допускающих это устройств; это не GATT-соединение и не спаривание.
Наличие ответа не гарантируется.

Команда по существующему WS/CBOR: `{scan_mode: "active"}` или `"passive"`,
с обычными `request_id` и `boot_id`. Смешивание с другими операциями, повторы
ключа и неизвестные значения отклоняются. HTTP обслуживает только assets.

Backend сохраняет желание приложения сканировать, ждёт STOP_COMPLETE,
меняет параметры, ждёт SET_EXT_SCAN_PARAMS_COMPLETE, затем восстанавливает
сканирование при необходимости. Переключение на паузе не запускает сканер.
Ожидающий GATT OPEN согласуется с этим порядком; автоматического OPEN нет.

Состояние содержит фактический `scan_mode`, запрошенный `requested_scan_mode`,
`scan_mode_pending` и `scan_mode_supported`. `ok` команды означает принятие;
успешное применение видно в состоянии, ошибка SDK — в `backend_error`/`fault`.

## Проверки и границы

Native-тесты проверяют признаки, конфликты, приоритет, все ширины UUID, короткие
и повреждённые поля, solicitation, лимиты, scan-response cache и четыре SIG
профиля, включая OFF. Настоящий код ESP-IDF backend собирается также с
управляемым SDK test double: подтверждения start/stop/configure, смена на паузе,
выбор до старта, ошибочные режимы и отказ SDK проверяются без радиоустройства.
Тот же тест вызывает настоящий `set_scan_timing`: границы, неизменность applied
до completion, последний запрос, смена во время configure, сохранение паузы,
неверный конструктор и отказ асинхронного применения. Подтверждения fake SDK
не заменяют измерение радиоприёма.
Это проверка порядка вызовов, а не аппаратная приёмка active scan.

Веб-тесты проверяют CBOR, переключатель, новые колонки, сортировку, фильтр,
переводы и сохранение DOM. В preview есть синтетические пульт, часы с Heart
Rate/Battery и клавиатура. Полный снимок 32 наблюдений с радио-метаданными и
двумя объявленными функциями проверяется в существующем буфере 32 KiB.
Сложные пакеты/журнал по-прежнему ограничены ёмкостью транспорта.

Прошивка плат не выполнялась. Реальное получение дополнительных
Scan Response в активном режиме требует отдельной разрешённой аппаратной проверки.
