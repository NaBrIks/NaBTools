# EI-T5300: ключ владельца и аутентификация

Модуль Samsung реализует экспериментальную owner-аутентификацию исходного
SmartTag, шифрование команд звука и расшифровку событий кнопки. Движок и общий
GATT client не содержат UUID, ключей или правил Samsung. На EI-T5300 проверены
получение существующего ключа через Devices API, взаимная аутентификация и
включение звука (физически подтверждено владельцем). Аппаратное подтверждение
событий кнопки и надёжного Stop sound пока не получено: в тестовых сеансах были
обрывы соединения. Native-тесты декодера не заменяют этих проверок.

## Откуда получить ключ зарегистрированной метки

Первый путь — прочитать собственное устройство через SmartThings Devices API:
`GET https://api.smartthings.com/v1/devices/{deviceId}`. В описании `bleD2D`
предусмотрено поле `encryptionKey`. Это не запрос `/status` и не ключ координат
из Samsung Find. Наличие поля в контракте API не гарантирует, что конкретный
токен или серверный вариант его отдаст.

Исследование EI-T5300 описывает `encryptionKey` как shared secret, переданный
при регистрации. Его первые 16 декодированных байт — `masterSecret`. Скрипт
принимает только 16 или 32 байта, в hex, Base64 или Base64url. Отсутствие поля,
замаскированное значение или неожиданный размер — ошибка, а не новый ключ.
Сброс, удаление устройства, повторная регистрация и новые ECDH-параметры для
извлечения существующего ключа не используются.

`tools/smarttag_owner_key.py` запрашивает PAT через скрытый ввод, показывает
только названия BLE-устройств и сохраняет credential выбранной метки в
игнорируемую папку `local/`. PAT не сохраняется. Достаточно прав показа и чтения
устройств; управление не требуется. По документации SmartThings новые PAT
действуют 24 часа. `401` на списке устройств означает отказ доступа к API,
а не ошибку BLE-аутентификации; точная причина не выводится из кода статуса.

```sh
python tools/smarttag_owner_key.py
```

Альтернатива — официальный SmartThings CLI с браузерным OAuth. CLI сам хранит
свои OAuth credentials в стандартном пользовательском хранилище; скрипт не
выгружает их и не выводит полный ответ API. Доступ CLI подтверждает владелец в
браузере. Используется отдельный профиль `nabtools-owner` и только команда чтения
`devices`, несмотря на более широкие возможности самого CLI.

```sh
npm install --prefix local/smartthings-cli --no-audit --no-fund @smartthings/cli
python tools/smarttag_owner_key.py --cli
```

В локальной установленной копии CLI адаптер заменяет автоматический вызов
`open()` на передачу адреса `/start` нашему скрипту. Адрес печатается для ручного
открытия браузера, без запуска PowerShell из Node. OAuth, PKCE и API остаются
официальными. Неизвестная структура CLI отвергается, без произвольного патчинга.
Этот путь подготовлен для CLI 2.1.2; результат входа зависит от сервера Samsung.

Можно импортировать уже полученный JSON-ответ о конкретном устройстве через
`--response <private-device.json>`. Он обрабатывается локально. Выходной файл
никогда не перезаписывается автоматически. Поле `device_id` — облачный ID, а не
текущий BLE MAC. Сам credential не устанавливает соответствие с вращающимся
адресом. В этой реализации экземпляр и попытку аутентификации выбирает приложение
или пользователь; доказательство ключом проверяется для конкретного соединения.

Если Devices API не отдаёт ключ, подтверждённого универсального экспорта из
обычного SmartThings здесь нет. uTag делегирует BLE-шифрование службе SmartThings,
поэтому установка uTag сама по себе не является экспортом ключа. Работа с
телефонным кэшем/модификацией приложения — отдельный возможный исследовательский
путь, без гарантии для каждой версии приложения; он не реализован этим скриптом.

## Граница приложения и модуля

`SmartTagOwnerAccess` передаётся в `SmartTagModule`. Его `load` Action получает
`DeviceId`, адрес текущего экземпляра и буфер на 16 байт. Приложение выбирает
credential и отвечает за его долговременное хранение. Callback вызывается только
по явной `owner.authenticate`, в контексте движка. Ключ не передаётся через
универсальные команды вебки, CBOR сообщений или диагностические логи.

`SmartTagCrypto` инъецирует RNG, SHA-256 и AES-128-CBC без padding. Padding,
KDF, состояния протокола и счётчики принадлежат Samsung-модулю.
`integrations/espidf/samsung/smarttag_crypto.hpp` предоставляет адаптер mbedTLS и
аппаратного RNG ESP-IDF. Без provider/crypto исследовательский GATT доступен,
owner-команды недоступны. STRUCT и CBOR остаются независимыми outputs.

Для временного исследования пример допускает приватный
`smarttag_owner_secret.hpp`, созданный из локального credential:

```sh
python tools/smarttag_owner_key.py --credential local/smarttag-owner.json --firmware-header examples/research/main/smarttag_owner_secret.hpp
```

Заголовок игнорируется Git. Это development-provider одного ключа, который
пробуется только для вручную выбранного экземпляра. Он встраивает секрет в
прошивку: такие binaries тоже нельзя публиковать. Для продукта приложение
предоставляет собственное хранилище/защиту; прошивка не сохраняет credential в
NVS автоматически. Выключение provider — удаление приватного заголовка перед
следующей сборкой. Секреты не входят в публичные примеры и тестовые fixtures.

## Протокол и команды

1. `connection.connect` выполняет discovery через общий GATT.
2. `owner.authenticate` подписывается на NONCE и ENONCE, генерирует случайный
   `nO`, получает `nT` и обменивается AES-CBC/PKCS7 доказательствами строки
   `smartthings`. `AKo = SHA256(masterSecret || 00000001 || bleAuthentication)[0:16]`.
   Встречное доказательство проверяется в двух точных вариантах: строка из
   11 байт + PKCS7(5) и наблюдённая EI-T5300 строка с завершающим NUL + PKCS7(4).
   Это сравнение всего блока, а не принятие произвольного суффикса/префикса.
   Только корректное встречное доказательство и завершение записей открывают
   дальнейшие операции. ACK записи сам по себе не подтверждает аутентификацию.
3. Session key — `SHA256(masterSecret || 00000001 || nT)[0:16]`, IV — `nT`.
   Исходный ключ и ключ аутентификации удаляются из состояния после их использования.
4. `button.observe` подписывается на кнопку и отправляет отдельные зашифрованные
   настройки press и hold. `alert.start` / `alert.stop` отправляют opcode 1 / 0
   в обнаруженную OWNER_ALARM. Это подтверждённая запись GATT, а не гарантия,
   что физический динамик уже прозвучал.
5. Команда содержит 32-битный LE counter, opcode и arguments, затем PKCS7.
   Первый исходящий counter — 1. Ошибка/неоднозначный результат записи закрывает
   сеанс; ciphertext с тем же counter автоматически не повторяется.
6. После расшифровки, проверки длины/padding, кода и возрастания counter события
   кнопки выдаются как `press`, `hold`, `double_press`. Неизвестные/повторные
   пакеты не становятся нажатиями. CBC этого протокола не добавляет MAC;
   проверка формата/counter не является отдельной криптографической подписью события.

События STRUCT приходят через `SmartTagActions::button`. Прямой CBOR имеет schema
`nabtools.samsung.smarttag.button.v1` и поля `type`, `action`, `counter`,
`authenticated`, `button_decoded`. Общий журнал/WS и веб-просмотр не знают
Samsung-протокол. Сырые GATT сообщения остаются отдельной диагностикой.
Auth nonce/proof не включаются в её CBOR `raw`; ключи не выдаются ни в одном output.

В таблицах исследования один UUID `d19ddd83...` подписан и как MODEL_NAME,
и как Privacy ID Seed. Он обозначен `model_or_privacy_seed_unverified` и не
читается автоматически как открытое имя. Для имени используется стандартная
Model Number String `0x2A24`, если обнаружена; firmware/cipher читаются отдельно.

Разрыв соединения, удаление экземпляра и ошибка auth сбрасывают сеансовые ключи.
Для повторной попытки требуется новое соединение, без повторных SDK-подписок
поверх старых. Адресные поколения отсекаются общим GATT-механизмом. Протокол
ожидает callbacks/ошибки транспорта; отдельного таймера handshake в модуле пока
нет, ожидание можно завершить явным Disconnect.

## Проверка и источники

Native-тест на Windows использует CNG как независимый crypto-provider и сверяет
KDF/AES с фиксированными векторами, подготовленными Python cryptography. Проверены
неверное доказательство, короткий nonce, padding, replay, оба порядка indication
и write completion, оба точных варианта строки proof, отсутствие команд до auth,
сброс сеанса при ошибке записи и удаление экземпляра из button Action.
Отдельные Python-тесты проверяют импорт, форматы, запрет redirect/посторонних hosts
и исключительное создание файлов. Эти проверки не доказывают совместимость
конкретной версии firmware метки.
