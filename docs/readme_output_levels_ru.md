# Уровни данных и знаний, 23.10.2026

Уточнение владельца: у одной обработки прибора могут быть несколько вариантов
выхода. Обычно приложение использует один, но имеет право подключить несколько
одновременно. Нельзя заставлять простой потребитель тащить полноценный сканер.

| Уровень | Назначение | Что знает потребитель |
|---|---|---|
| Структура | Маленькие законченные устройства, строгий контракт | C++ тип и заранее согласованный смысл полей |
| CBOR | Расширенные специализированные системы, очередь/браузер/события | Имена и версию прикладного контракта; общие C++ типы не нужны |
| CBOR/JSON с описаниями | Универсальный исследовательский инструмент | Получает описание типа, полей, единиц, состояний и событий от модуля |

Это варианты использования знаний о протоколе, а не обязательная цепочка
«структура → CBOR → JSON». Прямой CBOR остаётся допустимым и желательным.
JSON может быть представлением того же описания на стороне вебки; обязательный
JSON DOM на MCU не нужен. Контракт CBOR не должен зависеть от совпадения флагов
компиляции у отправителя и получателя.

## Кто собирает получателей

Приложение при создании экземпляра передаёт нужные Actions. BT владеет
экземпляром и ресурсами протокола. Каждая обработка один раз проверяет/разбирает
пакет, обновляет своё состояние и вызывает подключённые выходы. Нет требования
одновременно создавать промежуточный объект всех форматов.

Actions заимствуют данные только на время вызова. Приложение владеет callback
контекстом; очередь, журнал, веб и постоянное хранение принадлежат получателям.
При необходимости нескольких получателей одного CBOR приложение может поставить
свой fan-out Action. Движок не обязан хранить журнал, форматировать веб или
определять, сколько потребителей нужно приложению.

Флаги STRUCT/CBOR в текущем коде означают включение кода этих выходов в firmware.
При включённых обоих выходах конкретные Actions всё равно выбираются при
создании экземпляра; пустой Action не вызывается. Это не переключение формата
CBOR на проводе и не требование иметь такие же флаги у потребителя.

## Распознаватели

Аналогичное разделение применимо к распознаванию:

- Минимум: `matches(view)`/результат проверки пакета — «моё/не моё».
- Для исследователя: название типа, свидетельства распознавания, уверенность/
  ограничения, доступный обработчик и известность текущего варианта пакета.

`FD5A` с проверенным контейнером service data позволяет распознать формат
Samsung SmartTag, но не доказывает подлинность, модель или принадлежность
конкретной физической метке. Company ID Samsung сам по себе недостаточен.
Распознавание не создаёт экземпляр. Кнопка «Добавить» — решение приложения,
которое вызывает фабрику подходящего модуля через механизм движка.

## Описания знаний: предложение следующего шага

Первые два уровня реализуются текущими Actions. Полного третьего уровня пока
нет: универсальная вебка умеет показывать поля CBOR, но ещё не получает
семантические описания единиц/событий. Предлагаемая формализация, не принятый ABI:

```cpp
// Optional protocol knowledge module; absent from small firmware.
struct MessageDescription; // schema/version, kind, field descriptions
struct DeviceTypeDescription; // protocol key, label, supported messages/actions
// Protocol packet parser and application outputs do not depend on these types.
```

Начальный состав описания сообщения: стабильная схема/версия; `kind`
(state/event/observation); поля с именем или путём, типом и смыслом; единица,
масштаб/точность, перечисления, диапазоны и признак необязательного значения;
для событий — что считается событием и как определяется повтор.

Рекомендация: выдавать описание типа отдельно и по запросу, а частые сообщения
связывать с ним по schema/version. Это экономит повтор метаданных. Такой режим
ещё не утверждён владельцем как обязательный: возможны самостоятельные
описанные сообщения для экспорта/захвата и ссылки на общий каталог.
Описания протокола/прибора принадлежат модулю устройства; SIG остаётся отдельным
источником стандартных имён и знаний BT и не заменяет прикладное описание.

Текущая интеграция держит `MessageInfo` отдельно от готовых bytes CBOR.
Исследовательское приложение кладёт их в транспортный контейнер и свой
ограниченный журнал, не декодируя сообщение на MCU. Конкретное приложение
может отправить те же bytes прямо в свою очередь вместо этого контейнера.
